# Implementation plan: BTP Plant Disease VR (Farm → Lab)

## Context
`Docs/PLAN.md` describes a VR experience: a farm (default scene) where the user selects one of seven plants, then a lab where they view it and run an illustrative Tomato/Early Blight recovery demo. The project is currently an empty URP template on **Unity 6000.5.5f1**, with only `SampleScene`, no scripts, and no XR packages. This plan turns the spec into ordered, verifiable build steps based on what the folder actually contains.

## What the folder analysis found (gaps the spec does not cover)
| Finding | Impact | Plan response |
|---|---|---|
| Meshy FBXs are **huge**: Apple_new 356 MB, Bell Pepper 187 MB, Tomato 70 MB, Strawberry_1 25 MB, Tomato_asset 237 MB, plus 20–28 MB textures | Too heavy for Quest 2 (likely millions of triangles each) | Decimate with **Blender 5.2** (installed) in headless batch → `*_opt.fbx`, textures capped at 2048 (lab) and 1024 (farm LOD) |
| `sci-fi_lab.glb` 468 MB, `spa.glb` + textures, `bermuda+grass.fbx`, `apple_tree_split` 243 MB, `Apple/`, `Strawberry/`, `Tomato_1/`, `Tree-Fruit_3d/` are unused | Slow imports only. Unreferenced assets don't go into builds | Leave them in place, don't reference them. The lab is built from Unity geometry (the spec allows this) |
| `.glb` files use `DefaultImporter` | Corn is not usable yet | glTFast package re-imports `maize_corn_plant.glb` |
| Cherry looks like a SpeedTree export (`.stmat`, opacity/subsurface TGAs) | Needs alpha-clip URP material | Build a URP Lit material by hand with alpha clipping from `Cherry1_Opacity.tga` |
| Meshy models use one baked texture atlas (no separate leaf submesh) | Can't swap only the leaf material | Use the spec's "derived leaf mask": an editor tool builds a leaf mask from the albedo hue, and a Shader Graph uses it to blend leaves only |
| Android already uses **Vulkan (with GLES3 fallback), IL2CPP and ARM64**. But the min API is 26, the stereo path is Multi-Pass, there are no XR loaders or `Assets/XR` folder, and the only build scene is `SampleScene` | Won't run on Quest yet | Phase 1 configuration (only what's missing) |
| Unity Editor is running and `unity` CLI is at `%LOCALAPPDATA%\Unity\bin\unity.exe`; Android module installed | Scenes and prefabs can be generated by editor scripts or CLI | Use editor scripts, so the setup can be repeated and reviewed |
| Reference images exist at the paths given in the spec | — | Copy them into `Docs/References/` |

## Phase 0: Docs and references
1. Copy the 3 reference images to `Docs/References/` (`plant_types.png`, `farming_land.png`, `lab.png`).
2. Write `Docs/Master_Prompt.md` = PLAN.md content with relative image embeds, plus asset map, scene flow, interaction rules, demo-data label, build targets, acceptance checks, and a **Missing assets: Grape, Peach** section.

## Phase 1: XR foundation
1. Add to `Packages/manifest.json`: `com.unity.xr.management`, `com.unity.xr.openxr`, `com.unity.xr.interaction.toolkit` (3.x), `com.unity.xr.hands`, `com.unity.cloud.gltfast`. Import the XRI **Starter Assets** and **Hands Interaction Demo** samples (XR Origin with controller + hand rays, poke, teleport, snap turn).
2. OpenXR: Android → Meta Quest Support feature, Hand Tracking Subsystem, Meta Hand Tracking Aim. Windows → Oculus/Valve/Khronos controller profiles, plus Hand Tracking Subsystem (activates only when the runtime supplies hands).
3. Meta Quest build profile: keep Vulkan/IL2CPP/ARM64/Linear, drop the GLES3 fallback, set the OpenXR render mode to Single Pass Instanced, and raise the min API to the level the Meta Quest build profile requires (it's currently 26). PC build profile: Windows 64, DX11.
4. Quality levels: **Quest2** (based on `Mobile_RPAsset`: MSAA ≤ 4x, soft shadows off, shadow distance ~20 m), **Quest3** (same asset family, higher render scale and texture/LOD budget), and **PC** (`PC_RPAsset`).
5. `XRBootstrap.unity` holds the one persistent XR Origin (Starter Assets prefab), `InputActionManager`, `XRInputModalityManager` (switches between hands and controllers when tracking is lost), EventSystem with `XRUIInputModule`, FadeOverlay, SelectionState, and EnvironmentController. Locomotion is teleport plus 30° snap turn, with smooth move disabled. Build order: XRBootstrap, Farm, Lab. `SampleScene` stays untouched and out of the build.

## Phase 2: Asset pipeline
1. `Tools/blender_decimate.py` (run with `blender -b -P`): import FBX → Decimate modifier to a target triangle budget → export `Models_Optimized/<Plant>_Lab.fbx` (~50–80k tris) and `<Plant>_Farm.fbx` (~5–10k tris). Sources are exactly the seven paths in the spec's table (Tomato Lab uses `Tomato_asset` if it's cleaner after decimation).
2. `PlantPrefabBuilder` (Editor menu): for each plant, build the URP Lit material (albedo, normal; metallic/roughness packed into mask), normalize scale to real height (tree ~3–4 m, corn ~2 m, peppers/tomato ~0.8–1 m, strawberry/potato ~0.3–0.5 m), set pivot at ground via a parent root, add a `CapsuleCollider`/`BoxCollider` for selection, and set up an LODGroup (Farm) or single high LOD (Lab). Missing model → fail loudly.
3. Corn: confirm glTFast import, then extract it into a prefab.
4. Textures: max size 2048 for Lab, 1024 for Farm, ASTC on Android.

## Phase 3: Core runtime (`Scripts/Runtime`)
- `PlantDefinition` (ScriptableObject): `plantId`, `displayName`, `farmPrefab`, `labPrefab`, `hasRecoveryDemo`, short info text (species identity only).
- `PlantCatalog` (SO): list of 7 definitions; `TryGet(id)`; `Default = tomato`.
- `SelectionState` (bootstrap singleton): `CurrentPlantId`, `event OnPlantChanged`, `SelectPlant(id)`.
- `EnvironmentController`: `SwitchEnvironment(EnvironmentId.Farm|Lab)` → fade out → unload old additive scene → load target additive → find `SpawnAnchor` → move the XR Origin (`XROrigin.MoveCameraToWorldLocation` + match rotation) → fade in. Uses a busy guard against double-press.
- `FadeOverlay`: camera-attached quad, fades alpha by coroutine.
- `BootstrapLoader`: on start, loads Farm additively.
- `MissingAssetIndicator`: spawns a red "SETUP ERROR: <plant> model missing" placeholder in the Editor or dev builds.
- `RecenterControl`: a button/menu input that re-aligns the XR Origin to the current spawn anchor.

## Phase 4: Farm scene
- Generated by `SceneScaffolder` (Editor), then art-tweaked by hand: ground plane plus a distant low-poly terrain ring, raised soil beds (scaled cubes with a soil material), a central aisle (`TeleportationArea`), `TeleportationAnchor`s at viewing points, a timber fence (primitives), a water tower, a notice board, a procedural skybox, and a warm directional light.
- Layout: low crops in beds along the aisle; Apple/Cherry along the orchard edge; Corn at the back so it doesn't block the view. Farm LOD prefabs are repeated with GPU instancing. One labeled **specimen** per species is at the aisle edge.
- `SelectablePlant` (on `XRSimpleInteractable`): on select → `SelectionState.SelectPlant` + an outline/emissive highlight + a `PlantNameCard` (world-space TMP canvas).
- Notice board has an **Enter Lab** button (`XRPokeFollowAffordance` + ray). If there's no selection, Tomato is used.
- Teleport-only layers: beds and scenery aren't on the teleport layer mask.

## Phase 5: Lab scene and UI
- Glasshouse from primitives (frames plus a translucent glass material), a mountain backdrop (skybox/plane), cool lighting, and a central pedestal with `LabPlantDisplay` (spawns `labPrefab` for the current selection and responds to `OnPlantChanged`).
- World-space canvases placed in an arc ~1.2–1.5 m from the user, 1.0–1.4 m high, text ≥ 24 px at a scale of 0.001:
  - **Plant panel**: 7 toggle buttons from the catalog (Grape/Peach are not in the catalog).
  - **Plant Information panel**: name, short identity text, and a small rotating 3D preview on its own turntable (asset-backed, no render texture needed).
  - **Recovery Demo panel**: see Phase 6. Non-tomato plants show "Tomato demo only" and a **View Tomato Demo** button that calls `SelectPlant("tomato")`.
- A **Return to Farm** button at a fixed spot left of the entrance.
- Shared `VRButtonStyle`: hover/press/selected colors (charcoal `#1E2328CC`, cyan `#22D3EE`, white text). `TrackedDeviceGraphicRaycaster` on every canvas.

## Phase 6: Tomato recovery demo
- `TomatoRecoveryData` SO: 6 rows exactly from the spec's table, and Week 3 flagged "Demo treatment applied". A permanent header reads "Illustrative prototype – not diagnostic or treatment advice".
- `TomatoRecoveryDemo`: `CurrentWeek`, Previous/Next/Week 1–6 buttons/Reset (Reset only resets the week, not the selection). Updates metric bars and the timeline highlight.
- Visuals: two tomato instances on either side of the pedestal (diseased fixed at Week 1, current week on the other side), separated by an emissive cyan divider.
- `LeafMaskBaker` (Editor): reads the tomato albedo and writes a mask texture (green-hue pixels = 1). `LeafDisease.shadergraph`: `lerp(albedo, blight color + procedural concentric spots, mask * _Severity)`. `_Severity` = disease severity / 100 via `MaterialPropertyBlock`. Fruit (red) and soil stay unaffected. Stems may be partly masked; fix by painting the mask if needed.

## Phase 7: Validation and optimization
- `ProjectValidator` (Editor menu): checks that the catalog has 7 entries with non-null prefabs, that Grape/Peach are absent, that the build scene order is Bootstrap/Farm/Lab, and that there's exactly one XR Origin, EventSystem and AudioListener at runtime.
- Quest 2 budget: ≤ 150k tris visible, ≤ 150 SetPass/draw calls, 1 real-time shadowing light, stable 72 FPS (OVR Metrics / Profiler over ADB).

## Verification
1. EditMode tests (Test Framework already installed): catalog integrity, `SelectionState` default = tomato, recovery data matches the table, Reset behavior.
2. Play Mode in the Editor with the **XR Device Simulator**: farm → select each of 7 plants → Enter Lab → correct model → step weeks 1–6, jump, Reset → View Tomato Demo from another plant → Return to Farm (selection kept). Confirm no duplicate XR Origin.
3. Build the Quest APK and the Windows player from their build profiles; check that both compile. The Editor currently has this project open, so build from inside it, or close it before using the `unity` CLI in batch mode.
4. On device: Quest 2 (FPS baseline), Quest 3, and PC VR through Link/SteamVR. Test controllers, teleport, 30° snap turn, hand pinch/poke on Quest, and controller fallback on PC.

## Execution order
Phase 0 → 1 → 2 (longest; Blender batch) → 3 → 4 → 5 → 6 → 7. Each phase ends with a compile check and a Play Mode smoke test.
